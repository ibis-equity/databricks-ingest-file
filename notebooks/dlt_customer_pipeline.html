Lakeflow DLT

DLT Customer Pipeline

This is a Lakeflow Spark Declarative Pipeline (formerly Delta Live Tables) that processes customer data through the medallion architecture. The pipeline is designed to ingest raw source records, clean and normalize them in the Silver layer, and publish business-ready analytics in the Gold layer.

Project docs: Project Functional Narrative  |  Executive Narrative

1. Purpose of the pipeline

The DLT customer pipeline implements a multi-layer customer intelligence system that turns raw customer data into reusable analytical assets. It follows the standard Bronze → Silver → Gold model used in modern lakehouse architectures.

In practical terms, this pipeline is built to answer questions like: what customer records exist, how clean are they, where are the revenue patterns, which customers are key spenders, and which emails or geographic patterns are most valuable.

The design gives the organization a clean separation between raw data, curated data quality layers, and final business reporting datasets.

3. Core components

Schema discovery

bronze_schema_catalog inventories the columns and data types for all bronze source tables. This exposes schema drift and helps standardize downstream transformations.

Bronze union

customers_bronze_all loads and combines all bronze tables using unionByName(..., allowMissingColumns=True) while adding a source_table column.

Reference data

zip_lookup enriches ZIP codes with city/state values, and the pipeline gracefully falls back if the lookup table does not exist.

Quality monitoring

pipeline_zero_record_alerts and the DQR table help teams detect empty datasets and null-heavy columns.

4. Bronze layer: dynamic source discovery

A key technical strength of this pipeline is that it does not assume a fixed table inventory. Instead, it dynamically inspects the bronze schema, discovers all source tables, and loads them as a unified raw customer dataset. This makes the pipeline much more resilient when new source tables are introduced.

  • Auto-discovers all tables in the bronze schema
  • Skips broken or missing tables without failing the entire pipeline
  • Renames inconsistent fields such as customer_id → cust_id
  • Tracks the source of each row using source_table
  • Uses missing-column-tolerant union logic to combine datasets safely

This creates a flexible bronze intake pipeline that can adapt as upstream sources evolve.

5. Silver layer: cleaning, standardization, and quality rules

The silver layer is the core quality and normalization layer for customer data. It repairs broken values, standardizes names and addresses, fills missing values, and removes invalid records before they can propagate to analytics.

Area Processing
Standardization Trim strings, proper-case names, uppercase state fields, and consistent address formatting.
Repair Generate customer IDs, clean ZIP codes, fix email values, and assign placeholder emails when needed.
Financial cleanup Strip currency symbols, convert invalid amounts safely, and set invalid values to numeric-safe defaults.
Enrichment Use ZIP lookup to add city/state metadata and enrich provider information.
Deduplication Use window functions to keep the best record per cust_id and source_table.
Quality enforcement Reject invalid records that fail ID, amount, or ZIP checks.

The result is a more reliable customer dataset that is ready for governed downstream reporting and analytics.

6. DQ reporting and monitoring

The pipeline includes a data quality report table, customers_silver_all_dqr, which records null counts by column and source table. This provides visibility into where quality issues are concentrated and how the source data changes over time.

  • Tracks null completeness across columns
  • Supports source-level monitoring
  • Helps identify weak data quality areas before they reach the business layer

7. Gold layer: analytics datasets

The gold layer generates multiple purpose-built analytical tables for business use. These datasets are designed for segmentation, revenue analysis, operational reporting, and customer intelligence.

Customer value

customers_gold_rfm_clv combines recency, frequency, and monetary analysis to estimate customer value and segment behavior.

Revenue geography

customers_gold_revenue_by_geography aggregates revenue by state and city to expose market concentration and opportunity.

Trend analysis

customers_gold_revenue_trends_daily supports time-series monitoring with rolling averages and revenue growth rates.

Email intelligence

customers_gold_email_analysis highlights email provider patterns, revenue concentration, and personal vs corporate customer splits.

Other important datasets include segment summaries, top spenders, state KPIs, and duplicate email detection.

8. Operational model

The pipeline uses the legacy dlt API, with all tables defined as materialized datasets using @dlt.table() decorators. It relies on expectations to warn or drop invalid records at several layers.

  • @dlt.expect_all warns on issues while retaining records
  • @dlt.expect_all_or_drop drops records that violate critical rules
  • Includes logging, quality checks, and zero-record monitoring for observability

9. Business value

This pipeline provides concrete business value across several dimensions:

  • Customer segmentation and targeted marketing
  • Geographic strategy and revenue insight
  • Daily trend analysis and forecasting support
  • Customer intelligence by email, spend, and region
  • Operational data quality monitoring and governance
The DLT pipeline is not just a transformation flow; it is an operational data product that converts raw customer records into measurable business insight.

10. Notable design decisions

The pipeline includes a commented-out archival function that was intentionally disabled because DDL statements such as CREATE SCHEMA and DROP TABLE are not permitted within @dlt.table() decorators. That functionality was moved to a separate archival notebook.

The implementation is also based on the older DLT API, which is still functional but could eventually be modernized to use current Lakeflow patterns.

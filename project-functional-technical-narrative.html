Full Project Narrative

Databricks Ingest File

This project is a practical data ingestion solution for taking operational files from a watched directory, validating them, normalizing their structure, and loading them into Databricks Delta tables for downstream analytical use. It combines file detection, metadata enrichment, schema-safe SQL generation, and lakehouse ingestion into one coherent pipeline.

GitHub repository: https://github.com/ibis-equity/databricks-ingest-file

DLT pipeline documentation: notebooks/dlt_customer_pipeline.html

1. Executive summary

The Databricks Ingest File project solves a common real-world data problem: source systems often deliver data as CSV, JSON, or Parquet files, and those files need to be moved into a governed analytics platform without manual intervention. This project automates that intake process by watching a folder, discovering new files, reading them into a DataFrame, sanitizing schema issues, loading the records into Databricks Delta tables, and moving the original files to an archive location.

At a business level, the project reduces manual operational work and creates a dependable bronze ingestion layer. At a technical level, it demonstrates disciplined engineering: idempotent processing, metadata tracking, safe SQL generation, resilient file handling, and flexible operational modes.

2. What the project does in plain terms

Load to Delta

A file is placed into a monitored source directory, such as an inbox folder. The application detects the file using either a filesystem event listener or periodic polling. It then reads the file, validates that it is ready to ingest, standardizes column names, and appends metadata such as ingestion timestamp and source file name. The data is next written into a Databricks Delta table using generated SQL and finally moved to a processed archive after a successful load.

The system intentionally prevents duplicates by tracking the absolute path of files that have already been processed in a JSON state file.

3. IT pipeline associated with file ingestion

The project represents a complete file-based IT pipeline. It is not simply “copy a CSV into Databricks”; it is an end-to-end data landing workflow. Every new file follows a deterministic path: intake, discovery, validation, transformation, table creation, batch loading, and archival.

This is the operational core of the project. It turns a folder full of raw files into a controlled, auditable, production-style ingestion workflow.

4. File and folder behavior

The project is configured by source directory, file pattern, watch mode, processed directory, and state file. It can watch only the root folder or scan recursively, and it can optionally limit the directory depth when nested subfolders are used.

Configuration Purpose
--source-dir Defines the folder that receives new files
--pattern Filters file names, such as *.csv
--processed-dir Moves successfully processed files after ingestion
--state-file Stores a record of already processed files
--watch-recursive Allows nested directory ingestion
--watch-depth Restricts how deep recursive scanning goes

This design lets the process fit into both simple local folders and more complex ingestion networks where files are dropped by upstream systems into a staging area.

5. Technical architecture

File intake

The script uses watchdog for file system event hooks and a polling loop as a fallback when filesystem events are not reliable.

Data parsing

pandas reads CSV, JSON Lines, and Parquet files and turns them into a tabular DataFrame.

SQL generation

Type conversion, identifier quoting, and literal rendering are generated dynamically to keep the insert statements valid and secure.

Databricks integration

The project connects to Databricks SQL using the Databricks SQL connector and creates or updates Delta tables in a target schema.

The runtime is intentionally compact and script-first. The main logic lives in main.py, where discovery, normalization, connection setup, and loading all happen in one procedural flow.

6. Functional lifecycle of a dropped file

When a file is dropped into the destination folder, a file-detection event or a periodic scan picks it up. The system checks that the file still exists, is not locked by a writing process, and is not already in the processed set.

After the file passes readiness checks, it is opened, parsed, and normalized. Column names are sanitized so they conform to database-friendly naming rules. For example, spaces, punctuation, and mixed casing are converted into lowercase underscore-based names. Metadata columns are added before insertion so every row carries provenance.

The file is then inserted into a unique Delta table. Table names are generated with a schema name, a table prefix, a timestamp, the sanitized file stem, and a deterministic SHA1-derived hash. This creates a stable but unique landing target for each upload. Once the upload succeeds, the original file is moved to a processed archive directory, and the state store is updated.

7. How file data becomes usable data

The project does more than just transport raw data. It turns heterogeneous external files into structured data suitable for analytics and downstream processing.

  • Column normalization: ensures consistent schema names across files
  • Type inference: maps pandas dtypes to Databricks SQL types
  • Metadata enrichment: adds _ingested_at and _source_file
  • Batch inserts: avoids oversized SQL payloads and improves reliability
  • State tracking: prevents duplicate ingestion on repeated runs

The resulting tables become data assets that can be consumed by BI tools, data quality checks, and further transformation layers.

8. Data quality and resilience

Reliability is a core design principle. The project includes safeguards against common ingestion risks:

  • It waits briefly if a file is still locked during write operations.
  • It skips files that already appear in the processed state ledger.
  • It catches exceptions and continues monitoring without crashing the whole loop.
  • It uses generated batch SQL instead of large single-row inserts.
  • It stores processed files in an archive rather than deleting them immediately.

These choices make the project suited for production-like environments where file drops are irregular but need to be handled reliably and safely.

9. Relationship to the DLT customer pipeline

The file ingestion utility is the intake layer for raw external data. Once files are landed in a destination folder and ingested into Databricks, the downstream DLT customer pipeline can consume that data as a raw source and process it through the medallion architecture.

In the project’s DLT-based customer processing model, files arriving from upstream systems are treated as raw source records. The pipeline then discovers bronze tables, creates a schema catalog, joins with reference data, enforces quality rules, and separates the data into Bronze, Silver, and Gold layers.

Raw file drop
→
Bronze intake
→
Schema discovery
→
Silver cleaning
→
Gold analytics

In practical terms, the dlt_customer_pipeline operates after the landing layer has brought in source files. It discovers source tables in the bronze schema, standardizes naming and values, deduplicates records, enriches with ZIP data, and then creates gold-level datasets such as RFM analysis, revenue by geography, state KPIs, email analysis, and duplicate email detection. The result is a business-ready customer intelligence layer built from raw input files.

10. Bronze → Silver → Gold process in the DLT pipeline

Layer Purpose Typical behavior
Bronze Raw ingestion Auto-discovers bronze tables, adds source_table, unions data, and logs schema metadata.
Silver Cleaning and standardization Normalizes names, fills nulls, repairs email and ZIP values, deduplicates records, and drops invalid rows.
Gold Business analytics Builds RFM, CLV, segment summaries, revenue trends, geographic KPIs, and email intelligence tables.

This means the ingestion utility and the DLT pipeline are complementary. The file ingestion layer brings in raw files; the DLT layer transforms and standardizes them into analytic-ready datasets.

11. Security and governance

The project supports secure Databricks connectivity through environment variables, Databricks secret scopes, and Azure Key Vault-based retrieval when needed. This reduces the risk of embedding credentials directly into scripts and supports safer production deployment patterns.

  • Environment variables are used first when available.
  • Databricks secret scopes provide a repeatable secure configuration model.
  • Azure Key Vault offers an alternative secret source for deployment environments.

The DLT pipeline further strengthens governance with source lineage, schema metadata tracking, expectations, and operational monitoring.

12. Business value and final assessment

This project is valuable because it closes the gap between file-based operational inputs and the analytics platform. It provides a clear, repeatable, and operationally safe way to land raw data, turn it into usable records, and prepare it for the next stage of analytical processing.

The DLT customer pipeline adds the next layer of intelligence: once files are dropped, discovered, and landed, the bronze/silver/gold architecture cleans and standardizes those files, enriches them, and converts them into high-value customer analytics. Together, these components form a production-ready data ingestion and processing pattern.

In summary, this project is both a practical file ingestion utility and the first stage of a modern lakehouse pipeline — bringing raw files in, validating them, and setting them up for trustworthy downstream analytics.

Project Narrative

Databricks Ingest File

This project is a practical file-ingestion utility designed to detect local source files, normalize them into tabular data, and push them into Databricks Delta tables in a repeatable, resilient, and operationally friendly way. It blends file-watching automation, schema-safe SQL generation, secure credential handling, and an ingestion lifecycle that moves completed files into a processed archive while tracking what was already uploaded.

Repository: https://github.com/ibis-equity/databricks-ingest-file

1. Functional overview

At a functional level, the project is not a generic ETL framework. It is a focused ingestion engine for landing files from a watched directory into Databricks. The system watches a source directory, looks for matching files (by name pattern such as *.csv), validates that the file is ready to read, and then creates or updates a Delta table in Databricks to receive the file contents.

Once the file is processed, the script saves a local state record so the same file is not re-imported on a later run, and then moves the file to a processed directory. This gives the project a clean batch and event-driven operational model: it is safe for one-time ingestion, continuous ingestion, and file-drop workflows.

Core business capability

Auto-ingest new files into Databricks without manual API calls or manual table creation.

Supported input formats

CSV, JSON Lines, and Parquet files, each read into a pandas DataFrame before being converted to SQL inserts.

Operational model

Event-driven watching by default, with a polling fallback when needed.

The ingestion flow is intentionally simple but robust. It begins by discovering files in a configured source directory. When a matching file is found, it confirms the file still exists, is a regular file, and is not locked by another process. The script then reads the content into a DataFrame, sanitizes column names, adds metadata columns, and creates a unique Delta table name based on the schema, timestamp, sanitized file stem, and a deterministic hash.

The resulting data is inserted in batches using generated SQL values. The file is then moved to a processed folder and logged in a JSON state file so future runs do not duplicate the ingestion.

3. Technical architecture

Primary runtime

The main runtime logic lives in main.py and consists of argument parsing, discovery, file processing, Databricks connection setup, and the watch loop.

Data access layer

It relies on pandas for tabular parsing and the Databricks SQL connector for direct SQL execution against a warehouse.

Filesystem automation

The watchdog library is used to listen for file events, with a polling fallback for environments where event watchers are unavailable or insufficient.

State management

A JSON state file stores processed absolute paths, enabling idempotent behavior across application restarts.

Key technical characteristics

  • It is a Python-based, script-first ingestion utility rather than a packaged service.
  • It creates a schema if it does not yet exist.
  • It creates a new Delta table for each file upload instead of appending to a single long-lived landing table.
  • It uses safe SQL quoting for identifiers and literal rendering for values.
  • It handles concurrency-sensitive file processing by waiting briefly when a file is still being written.

4. File processing lifecycle

The project’s operational lifecycle is deterministic and straightforward:

Stage Behavior Implementation detail
Discovery Searches the configured directory for matching files. discover_files() walks a directory tree or a single directory depending on recursive settings.
Filtering Skips files that have already been processed. Absolute path strings are kept in a JSON state set and compared before execution.
Read and normalize Reads file content and standardizes column names. read_input_file() reads CSV/JSON/Parquet and applies sanitize_column_name().
Metadata augmentation Adds ingestion metadata to every row. _ingested_at and _source_file are appended before insert.
Table creation Ensures the target schema and Delta table exist. ensure_schema() and ensure_table() execute CREATE SCHEMA IF NOT EXISTS and CREATE TABLE IF NOT EXISTS.
Batch insert Rows are inserted into the table in manageable chunks. batched() splits row tuples before executing multi-row INSERT INTO statements.
Completion Archives the file and persists state. move_to_processed() moves the file and save_state() writes the state ledger.

5. IT pipeline associated with file ingestion

The file pipeline in this project is the operational backbone of the ingestion process. It begins when a file arrives in a source directory and ends when that file has been transformed into a Databricks table and moved into a processed archive. The pipeline is intentionally simple but complete: it includes intake, validation, parsing, metadata enrichment, schema creation, data load, archival, and state tracking.

In practical IT terms, the pipeline behaves like a bronze ingestion workflow. Files are first detected either by a filesystem event or by periodic scanning. The application checks whether they are valid targets, ensures they are not partially written, and filters out duplicates already stored in the local state ledger. Once accepted, files are read into a DataFrame, their columns are sanitized, and additional metadata such as _ingested_at and _source_file is added to each row.

After parsing, the system prepares the landing area in Databricks. It ensures the schema exists, then creates a uniquely named Delta table and loads rows in chunks using generated SQL. This is designed to keep the process resilient, synchronized, and operationally safe. Once the upload succeeds, the original file is moved to a processed directory and the state file is updated so the same file is not picked up again on the next cycle.

This makes the project an IT pipeline for file-based data intake rather than a one-off utility: it is built to run repeatedly, handle incoming file drops reliably, and feed raw operational data into a lakehouse architecture with traceability and control.

6. Data normalization and SQL generation

One of the project’s most important technical details is how it turns arbitrary external files into safe transactional SQL. This is not just a CSV copy utility. It deliberately normalizes column names and generates valid Databricks SQL for identifiers, types, and values.

  • Column sanitization: spaces, punctuation, and mixed casing are collapsed into lowercase underscore-based names.
  • Type mapping: pandas dtypes are interpreted into Databricks SQL types such as BIGINT, DOUBLE, BOOLEAN, TIMESTAMP, and STRING.
  • Identifier quoting: schema names and table names are turned into quoted SQL identifiers to protect names with special characters.
  • Literal conversion: strings, booleans, dates, datetimes, decimals, and nulls are rendered into valid SQL literals.
sanitize_column_name(" Customer Name ") -> "customer_name"
quote_ident("schema.table") -> "`schema`.`table`"
to_sql_type("datetime64[ns]") -> "TIMESTAMP"
sql_literal("O'Hare") -> "'O''Hare'"

This is especially important because input files may come from downstream systems with non-standard headers and inconsistent casing. Without this conversion layer, Delta table creation and row insertion would be fragile and error-prone.

7. Unique table naming design

Each file upload is assigned a unique Delta table name so that every file is isolated into its own table. The design is intentionally built to prevent collisions and preserve some traceability in naming.

  • Base schema: etl-bronze-pipelne-data
  • Base table prefix: bronze-ingest-
  • Timestamp: YYYYMMDD_HHMMSS_microseconds
  • Sanitized file stem: a human-readable suffix
  • Hash: a deterministic 8-character SHA1 from the file stem

The pattern ensures that table names are unique even if multiple files are uploaded in the same second, and it also prevents names from exceeding the configured maximum using the MAX_FULL_TABLE_NAME_LENGTH guardrail.

8. Execution modes

The project supports two main execution modes, giving it flexibility across different operational scenarios.

Mode Purpose Behavior
event Continuous, file-drop-driven ingestion Uses watchdog to react immediately when files are created or moved into the watched directory.
poll Periodic scanning Periodically discovers files and processes those that are new, useful when filesystem events are not available.

Additional operational controls include --once for a single scan, --dry-run for parse-only workflows, recursive watching via --watch-recursive, and a subfolder depth limit through --watch-depth.

9. Reliability and safety features

  • Idempotence: processed files are tracked so repeated runs do not re-import the same artifact.
  • File lock handling: the script waits for a file to become available for exclusive access before reading it.
  • Graceful failure: exceptions are caught and logged without crashing the monitoring loop.
  • Batch inserts: prevents huge single statements from overwhelming Databricks or the SQL connector.
  • Safe removal: completed files are moved to a processed directory rather than deleted immediately.

10. Databricks connectivity and secrets

The ingestion runtime depends on Databricks connection variables: server hostname, HTTP path, and access token. These are read from environment variables by default, but the repository also contains secure patterns for secret management.

Environment-based configuration

The fastest and most typical pattern is to load values such as DATABRICKS_SERVER_HOSTNAME, DATABRICKS_HTTP_PATH, and DATABRICKS_TOKEN from the local environment.

Databricks secret scope

Scripts in the repo also support creating a Databricks secret scope and populating all required values for a repeatable deployment pattern.

Azure Key Vault

An alternative path uses Azure CLI and Key Vault to resolve secrets when environment variables are missing.

The project includes a healthcheck utility, databricks_healthcheck.py, which validates connectivity and optionally verifies cluster readiness before executing a query. This is useful for proving that the warehouse environment is alive and configured correctly before production loads begin.

11. Supporting utilities and adjacent capabilities

The repository is not limited to the core ingestion script. It includes adjacent utilities that deepen the data engineering story.

databricks_healthcheck.py

Performs SQL connectivity validation and cluster readiness checks using Databricks SQL and the Databricks Workspace API.

flatten-json/

Contains code to flatten nested JSON payloads into Delta tables, especially useful for complex records like customer or product data.

shopify_salsify/

Contains example ingestion logic for Shopify and Salsify sources using requests and Delta Live Tables (DLT) patterns.

12. Functional and technical summary

In essence, this project is a compact, practical bridge between local business files and Databricks Lakehouse storage. It automates the ingestion loop, handles multiple data formats, normalizes file content into a consistent schema, creates dedicated Delta tables for each upload, and tracks completion in a durable state store.

Technically, it is a Python utility built around pandas, SQL generation, Databricks connectors, file watcher automation, and operational safeguards. It is intentionally engineered for straightforward deployment in real-world ingestion pipelines where files appear at unpredictable times, metadata must be trusted, and table creation should be deterministic and resilient.

The project is best understood as a focused ingestion toolkit: small enough to run locally or in an automation host, but robust enough to serve as a foundation for bronze-layer ingestion into Databricks.
